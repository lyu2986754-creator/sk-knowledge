# Agentic RAG 服务

在现有 Java RAG 之上加一层 Python 的 Agent 编排，让"检索"从固定一步变成
由模型自主决定的多轮过程。

## 为什么需要它

实测发现：纯向量检索对**精确编号**不敏感。同一个问题

| 查询语句 | 第十三条的排名 |
| --- | --- |
| `个人信息保护法第13条规定的内容是什么？` | 完全没出现 |
| `个人信息处理者处理个人信息的合法性基础 第十三条` | 第 1 名 |

语料、向量库、嵌入模型都没变，**只改查询语句**。所以"查询改写 + 迭代检索"
是一个可预期的正收益方向。

## 实测效果（2026-09-27）

同一批 27 条评测 case、同一个知识库、同一个模型，**只切换执行模式**：

| 指标 | 朴素 RAG | Agentic RAG | 变化 |
| --- | --- | --- | --- |
| **全部通过** | 16/27（59%） | **24/27（89%）** | **+30pp** |
| 过程层检索命中通过率 | 81% | **100%** | +19pp |
| **术语辨析题检索命中率** | **50%** | **100%** | **+50pp** |
| 直接抽取题检索命中率 | 67% | **100%** | +33pp |
| 结果层要点命中通过率 | 89% | **96%** | +7pp |
| 拒答正确率 | 89% | 93% | +4pp |
| 平均耗时 | 2.2s | 3.3s | +50% |
| **总 token** | 13,944 | **62,178** | **4.5×** |

五类题型的检索命中率**全部达到 100%**。

**代价很明确**：token 4.5 倍、延迟 +50%。原因是每一轮检索都要一次完整的 LLM 决策调用。

> 所以这不是"无脑上 Agent"的理由，而是一个**成本-效果取舍**：
> 对精确条款类查询（条文编号、术语定义）值得用 Agentic；
> 对泛泛的开放问题，朴素模式性价比更高。

### 迭代过程（两次基于实测的修正）

最早的版本（v1）token 涨 3.6 倍。没有直接接受这个代价，而是拆开分析，发现两件事：

1. **多轮检索没有去重** —— 实测 10 个 case 累计 **67 条重复片段**，
   最严重的一条第二轮返回的 10 条与第一轮**完全相同**。
   去重后召回片段数 370 → 314（−15%）。
2. **曾把"判断信息够不够"和"生成答案"拆成两次调用** ——
   实测 token 反而从 50,683 涨到 **74,819（+48%）**，而要点指标还退了一点。
   回头检查发现这个拆分根本没必要：要的"停止决策"信号，原输出里本来就隐含了。
   **已回滚**。

最终版本（v3）= 去重 + 无新增反馈 + 判断与作答合并为一次调用。

## 健壮性与成本护栏

Agent 循环是自写的（遵循 `project.md` R5），所以"卡死、烧钱、单点抖动"这三件事
必须自己兜住。三个护栏都可配置，默认值有实测依据：

| 护栏 | 默认 | 依据 |
| --- | --- | --- |
| token 预算 | **12,000 / 轮** | 实测单条最大 3,720 的 3.2 倍；低于 8k 会误伤长问题 |
| 总体超时 | **60s** | 实测单条最大 4.7s 的约 13 倍，与 httpx 单次超时是两层 |
| 重试 | **2 次**（共 3 次尝试），退避 1s → 2s | 与 Java 侧 Spring AI 的 `maximumAttempts=3` 对齐 |

**触发时的行为**（三者都不静默）：

- **超预算** → 停止检索，用已有上下文强制收一个答案，`stoppedBy=token_budget`。
  预算是**软上限**：LLM 请求一旦发出就无法中途掐断，所以它管的是"要不要再开新一轮"，
  超限的那一轮仍会完整计费。
- **超总时** → 整轮判失败，前端出错误气泡（`error` 里带超时秒数）。
- **重试耗尽** → 整轮判失败，前端出错误气泡（`error` 里带最后一次的 HTTP 码）。

**只重试可恢复错误**：超时、连接失败、5xx、限流（429）、LLM 返回非法 JSON。
4xx 立即失败——重试一个 401 只是把失败延后。登录与历史读取刻意不重试：
前者错了重试也没用，后者失败只降级成"没有历史"，重试只会白推高整轮延迟。

配置项：`AGENT_TOKEN_BUDGET` / `AGENT_OVERALL_TIMEOUT` / `AGENT_MAX_RETRIES` /
`AGENT_RETRY_BACKOFF`。诊断事件里会带上 `tokenBudget` / `totalTokens` /
`overallTimeoutS` 快照，供评测平台区分"模型失控"与"预算本来设得宽"
（对应 `project.md` R3 的可复现要求）。

## 它在整体里的位置

```
RAG 前端（8080）
  └─ 模式开关：朴素 / Agentic
     baseURL = agentic ? http://localhost:8092 : http://localhost:8082

本服务（8092）          ← 你在这里
  └─ 内部跑 Agent 循环，检索走 Java 的 /api/retrieve

Java RAG（8082）
  ├─ /api/chat/...   现有问答链路（本服务不碰）
  └─ /api/retrieve   只读检索接口（本服务依赖它）
```

**朴素模式不经过本服务**，前端直接连 Java。因此对比两种模式时没有代理开销，
延迟数字可比。

## 接口

刻意与 Java 保持**完全相同的路径与事件名**，这样 RAG 前端只需要切换 baseURL，
其余代码（两步式调用、EventSource）一行都不用改。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/login` | 转发给 Java，复用它的鉴权（本服务不做自己的认证） |
| POST | `/api/chat/completions` | 收下问题，返回 sessionId |
| GET | `/api/chat/stream/{sessionId}/{knowledgeId}` | SSE 流 |

SSE 事件名与 Java 一致：`chatContextIdVo` / `content` / `diagnostics` / `done`。

## 启动

```powershell
# 首次：建虚拟环境并填密钥
cd D:\Project-self\AI qiyexiangmu\agentic-rag
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install httpx fastapi uvicorn python-multipart
copy .env.example .env    # 填 DEEPSEEK_API_KEY

# 之后每次：一条命令启动 / 重启
.\deploy\restart-agentic.ps1
```

`restart-agentic.ps1` 会按端口停旧进程、检查上游 Java RAG 是否可达、
后台启动服务并做健康检查，失败时打印日志尾部。

## 设计取舍

- **不引 LangChain / LangGraph 等重型框架**（遵循 `project.md` R5）。
  Agent 循环是自己写的，控制点全部可见——而这些控制点正是要被观测和评分的对象。
- **不做自己的鉴权**：登录转发给 Java，复用它的 JWT。少一套账号体系。
- **会话存在内存里**：本服务是本地单用户工具，会话 TTL 5 分钟，与 Java 侧一致。
